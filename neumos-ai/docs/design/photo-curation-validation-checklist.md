# Photo Curation 実データ検証チェックリスト

Phase 1（`editorial/` 計算プリミティブ + `photo-curation.ts` への責務統合）は
`agent/demo-video-phase0-1` ブランチでクローズした。本ドキュメントはPhase 2を
始める前に必要な**検証計画**であり、実装ではない。ここに書かれた項目は
「アルゴリズムが正しいか」ではなく「プロダクトとして成立するか」を確認する
ためのものであり、Phase 2はこの検証で見つかった事実から始めるべきである。

## 対象範囲

検証対象は `compressPhotoUrls` / `orderGalleryPhotos`
(`src/lib/engine/photo-curation.ts`) と、その基盤となる
`src/lib/editorial/{similarity,compress,arrange,gallery-layout}.ts`。
v1テンプレート・DBスキーマ・APIコントラクトは対象外（変更しない）。

## 検証規模

- 10店舗
- 50店舗
- 200店舗

段階的に規模を広げ、各段階で下記の観点を確認する。小規模で問題が出た場合は
規模を広げる前に修正する。

## 各店舗ごとに確認する観点

- **Hero duplication**: HeroとGalleryに知覚的に同一/酷似した写真が重複して
  出ていないか
- **Gallery diversity**: Galleryが「似た構図の羅列」になっていないか
  （バースト撮影の後の残存パターンを含む）
- **Burst-photo reduction**: 連写・エクスポート違いの写真群が適切に1枚へ
  畳まれているか（畳みすぎ・畳まなすぎ両方を確認）
- **Dark-image behavior**: 暗所写真でdHash判定が破綻していないか
  （誤って別写真と誤判定/同一判定していないか）
- **Portrait/Landscape mix**: 縦横比が混在する店舗でOccupy/Sequence判定が
  不自然に偏らないか
- **Single-photo stores**: 写真が1枚しかない店舗でIsolate判定・Hero/Gallery
  分担がクラッシュなく成立するか
- **Zero-photo stores**: 写真が0枚の店舗でパイプライン全体が安全に空配列を
  返し、既存v2のフォールバック表示が機能するか
- **Performance**: 写真枚数が多い店舗（50枚・200枚規模の入力）で
  `compressPhotoUrls`/`orderGalleryPhotos` の実行時間が許容範囲か
  （`selectDisplayPhotos`の12枚上限より前段の重複排除コストを含む）
- **Visual regression**: 既存v2（Phase 1適用前の表示）と比較して、
  見た目が改善しているか、少なくとも悪化していないか

## 検証データの制約

このプロジェクトの標準制約（外部API不使用・本番Supabase不使用・
本番環境不使用・ローカルのみ・追加費用ゼロ・データ捏造禁止）は本検証でも
維持する。「実店舗データ」を使う場合も、本番DBへの接続や外部APIの実呼び出し
を伴わない形（synthetic画像 + 実際にありそうな枚数・構図パターンの再現）で
実施方法を別途具体化する。

## Phase 2の起点

Phase 2は、上記検証で見つかった事実（例: 特定条件でHero重複が再発する、
暗所写真でdHashが機能しない、200枚規模で性能が劣化する等）から着手する。
検証前にアルゴリズムの拡張・新機能追加を先行させない。

## 実施記録: 合成データによる1回目のラウンド

22店舗（7カテゴリ、burst / diverse / diverse2 / dark / mixed-aspect /
single / zero / large50 / large200）を`/api/generate`経由でローカル生成し、
上記8観点を(a)ライブラリ関数(`compressPhotoUrls`/`orderGalleryPhotos`/
`buildPhotoPlan`)への直接テストと、(b)実際に描画されたプレビューページの
モバイルスクリーンショット、の両方で確認した。修正が必要な欠陥は0件。
詳細（スクリーンショット付き）は検証時に作成したレポートを参照（本ラウンドの
成果物はコミットせずクリーンアップ済みのため、要約のみここに残す）。

**確認できたこと**:
- Hero/Story写真がGalleryへ重複して出現するケースは全カテゴリでゼロ件。
- burst(連写想定)は6枚→1枚に正しく畳まれる。genuinely-diverseな6枚
  (象限・水平分割・放射・対角・三分割・コーナースポットの構図)は畳まれず
  6枚とも保持される。
- 暗所写真・写真1枚・写真0枚のいずれでもクラッシュしない。
- 50枚・200枚規模の入力でも、実際にdHashデコードするのは
  `selectDisplayPhotos`の12枚上限後のみのため、所要時間は入力枚数に
  ほぼ依存しない（50枚で約4.1秒、200枚で約2.5〜3.5秒）。

**Phase 1のスコープ外として記録するに留めた点**:
- mixed-aspect（縦横比混在）の店舗で、実際に描画されるGalleryグリッドは
  元の縦横比の違いを視覚的に吸収してタイルをほぼ均一に見せる。これは
  `PhotoStoryV2`（Phase 1では変更していない既存v2コンポーネント）のCSS
  グリッド挙動であり、`compress`/`arrange`/`gallery-layout`自体の欠陥では
  ない。将来Gallery品質改善に着手する場合の候補としてのみ記録する。
- 既存v2（Phase 1適用前）との視覚的な比較（visual regression）は本ラウンド
  では未実施。

**今回の検証方法自体について分かったこと（次回への申し送り）**:
- 合成テスト画像で「構図の違い」を作る際、細かい市松模様・縞模様は
  dHashの9×8ダウンサンプルで平均化されて消える。画像幅/9より十分大きい
  大域スケールのパターン（象限・水平分割・放射・対角等）でないと、意味のある
  distinctness信号にならない。
- dHashは絶対輝度ではなく勾配の符号を見るハッシュのため、同一構図で
  露出（明るさ）だけが違う2枚はdistance=0になる。これはバグではなく
  露出違いの同一構図写真を重複として扱う望ましい挙動だが、合成テスト画像で
  「多様性」を作る際は輝度だけでなく大域構造も変える必要がある。
- Hero/Gallery重複を生HTMLの文字列一致だけで判定すると誤検知する。
  SEO用のJSON-LD構造化データは方針上、重複排除前の生`photoUrls`を
  そのまま含んでおり、さらにNext.jsのRSCフライトペイロードが同じJSON-LDを
  もう一度シリアライズするため、単純な文字列カウントは実際の可視DOMの
  重複数を大きく過大に報告しうる。判定には`<script type="application/ld+json">`
  とフライトペイロード（`self.__next_f.push(...)`）の除外が必要。
- `src/lib/store.ts`はインメモリのため、`next start`プロセスを再起動すると
  既存の`requestId`は全て失効する。`public/`への新規ファイル追加もプロセス
  起動後には反映されないため、両方が必要な検証では
  「ファイル追加→サーバー再起動→生成し直し」の順序を守る必要がある。

**次に検証すべきこと**: 合成データはあくまで幾何学パターンであり、実際の
店舗写真が持つ照明の連続性・JPEG圧縮ノイズ・実際の構図の複雑さを完全には
代替できない。次のラウンドは、より写真らしい特徴を持つデータ（可能であれば
実店舗データ）での検証に進むのが妥当。
